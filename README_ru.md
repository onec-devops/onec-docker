# Onec Docker

[English](README.md) | Русский

Платформа 1С:Предприятия 8.3 в Docker. Сервер в контейнере удобен для разработки и тестовых
стендов: его легко поднять, пересоздать с нуля или перевести на другую версию платформы. Образ
`full` запускает тот же сервер вместе с клиентами платформы и виртуальным дисплеем.

СУБД в стеке нет, для серверных информационных баз понадобится отдельный PostgreSQL или
Microsoft SQL Server.

> [!WARNING]
> Сервер не рассчитан на доступ из интернета. У кластера нет администраторов, а Docker
> открывает его порты на всех сетевых интерфейсах хоста.

## Требования

- Дистрибутив платформы 1С:Предприятия 8.3 для Linux x86_64. Проект проверен на версии
  8.3.25.1633.
- Docker Engine с BuildKit или Docker Desktop.
- Docker Compose 2.24.4 или новее.
- Для сборки не меньше 8 ГБ свободного места на диске, а вместе с `full` не меньше 16 ГБ.

## Образы

| Образ | Состав |
|---|---|
| `onec-devops/1cv8-server` | Сервер 1С:Предприятия с сервером администрирования и утилитами `rac`, `ibcmd` и `ibsrv`. Клиентов в нём нет. |
| `onec-devops/1cv8-full` | Тот же сервер с клиентами, виртуальным дисплеем и VNC-сервером, через который дисплей виден с хоста, в том числе в браузере. Клиенты в нём запускаются прямо в контейнере, например для автотестов. По умолчанию ставится только тонкий клиент, толстый можно добавить. |

## Начало работы

1. Скачайте с https://releases.1c.ru дистрибутив платформы для Linux
   `setup-full-<версия>-x86_64.run` и положите его в каталог `distr/`. В каталоге должен лежать
   ровно один дистрибутив, имя файла не важно.

2. Скопируйте `.env.example` в `.env` и укажите в `ONEC_VERSION` версию платформы, например
   `8.3.25.1633`:

   ```sh
   cp .env.example .env
   ```

3. Соберите нужный образ, `server` или `full`:

   ```sh
   docker compose build server
   ```

   Получится образ `onec-devops/1cv8-server:8.3.25.1633` с тегом по версии платформы.

4. Запустите сервер:

   ```sh
   docker compose up -d
   ```

5. Проверьте, что кластер поднялся:

   ```sh
   docker compose exec server rac cluster list
   ```

> [!WARNING]
> Собранный образ содержит платформу 1С:Предприятия. Права распространять её лицензия этого
> проекта не даёт, поэтому не выкладывайте образ в публичный реестр.

## Настройки

Настройки сборки и запуска задаются в файле `.env`, шаблон со всеми переменными лежит
в [.env.example](.env.example). Обязательна только переменная `ONEC_VERSION`, без неё команды
compose не запускаются.

| Переменная | По умолчанию | Описание |
|---|---|---|
| `ONEC_VERSION` | | Версия платформы. Должна совпадать с версией дистрибутива в `distr/` |
| `COMPOSE_PROFILES` | | Сервис по умолчанию для команд compose, `server` или `full`, подробнее в разделе [Запуск сервера](#запуск-сервера) |
| `IMAGE_NAMESPACE` | `onec-devops` | Префикс в именах образов `onec-devops/1cv8-server` и `onec-devops/1cv8-full` |
| `NOVNC_PORT` | `6080` | Порт страницы noVNC образа `full` на хосте, подробнее в разделе [Запуск клиентов](#запуск-клиентов) |
| `ONEC_CLIENT_COMPONENTS` | `client_thin` | Компоненты через запятую, которые ставятся только в образ `full`, подробнее в разделе [Компоненты платформы](#компоненты-платформы) |
| `ONEC_COMPONENTS` | `server,ws` | Компоненты через запятую, которые ставятся в оба образа, подробнее в разделе [Компоненты платформы](#компоненты-платформы) |
| `ONEC_DEBUG` | `false` | Включает отладку, подробнее в разделе [Отладка](#отладка) |
| `ONEC_DEBUG_PORT` | `1550` | Порт сервера отладки |
| `ONEC_HOSTNAME` | `onec-server` | Имя, по которому клиенты подключаются к серверу, подробнее в разделе [Подключение к серверу](#подключение-к-серверу) |
| `ONEC_MAC_ADDRESS` | `02:1c:08:03:00:01` | MAC-адрес сервера, к нему привязываются программные лицензии |
| `ONEC_PORT` | `1540` | Порт агента сервера |
| `ONEC_RANGE_START` / `ONEC_RANGE_END` | `1560` / `1591` | Диапазон портов рабочих процессов |
| `ONEC_RAS_PORT` | `1545` | Порт сервера администрирования |
| `ONEC_REGPORT` | `1541` | Порт менеджера кластера |
| `SCREEN_WIDTH` / `SCREEN_HEIGHT` | `1920` / `1080` | Ширина и высота виртуального дисплея образа `full` в пикселях |
| `SCREEN_DEPTH` | `24` | Глубина цвета виртуального дисплея в битах |
| `SCREEN_DPI` | `96` | Плотность точек виртуального дисплея, от неё зависит размер шрифтов |
| `START_DISPLAY` | `true` | Запускать ли в образе `full` виртуальный дисплей, подробнее в разделе [Запуск клиентов](#запуск-клиентов) |
| `TZ` | `Europe/Moscow` | Часовой пояс контейнеров. От него зависит, какое время вернёт `ТекущаяДата()` на сервере |
| `VNC_PASSWORD` | | Пароль VNC-сервера образа `full`, не длиннее 8 символов. Его же спрашивает noVNC. По умолчанию пароля нет, подробнее в разделе [Запуск клиентов](#запуск-клиентов) |
| `VNC_PORT` | `5900` | Порт VNC-сервера образа `full` на хосте, подробнее в разделе [Запуск клиентов](#запуск-клиентов) |

### Компоненты платформы

Дистрибутив платформы состоит из компонентов, их список приведён в руководстве
администратора, в разделе [«Пакетная установка»](https://its.1c.ru/db/v8325doc#bookmark:adm:TI000001075).
Серверные компоненты перечисляются в `ONEC_COMPONENTS`, клиентские
в `ONEC_CLIENT_COMPONENTS`.

По умолчанию в оба образа ставятся `server` и `ws`. С компонентом `server` приходят кластер
серверов, сервер администрирования `ras` и утилиты `rac`, `ibcmd` и `ibsrv`, поэтому
отдельный компонент `server_admin` не нужен. Компонент `ws` добавляет движок файловых баз,
без которого `ibcmd` и `ibsrv` с ними не работают.

В образ `full` дополнительно ставится `client_thin`, тонкий клиент, который не открывает
файловые базы напрямую. Толстый клиент и конфигуратор не ставятся, чтобы образ был меньше.
Они попадают в образ, если указать в `.env` `ONEC_CLIENT_COMPONENTS=client_thin,client_full`
и пересобрать образ.

### Смена портов

Если стандартные порты на компьютере заняты, например установленным сервером 1С или другой
копией проекта, в `.env` можно назначить другие. Следующие значения сдвигают все порты на 1000:

```sh
ONEC_PORT=2540
ONEC_REGPORT=2541
ONEC_RANGE_START=2560
ONEC_RANGE_END=2591
ONEC_RAS_PORT=2545
ONEC_DEBUG_PORT=2550
VNC_PORT=6900
NOVNC_PORT=7080
```

### Отладка

Отладка включается строкой `ONEC_DEBUG=true` в `.env`. Сервер тогда запускается с ключами
`-debug -http`, а сервер отладки `dbgs` работает на порту из `ONEC_DEBUG_PORT`, по умолчанию
1550. Подключаться к нему нужно по адресу `http://onec-server:1550`, имя сервера должно
быть доступно так же, как при [подключении клиентов](#подключение-к-серверу).

### Файлы настроек платформы

Файлы настроек платформы, например `conf.cfg` и `logcfg.xml`, сервер читает из каталога
`/home/usr1cv8/.1cv8/1C/1cv8/conf`. Он находится внутри тома `srv-data`, поэтому настройки
удобнее держать в каталоге на хосте, подключённом на его место через `compose.override.yaml`.
Пример для сервиса `server`:

```yaml
services:
  server:
    volumes:
      - ./conf:/home/usr1cv8/.1cv8/1C/1cv8/conf:ro
```

Для технологического журнала в образе предусмотрен каталог `/var/log/1C`, он хранится
в томе `logs`.

Параметры файлов описаны в руководстве администратора, в приложении
[«Описание и расположение служебных файлов»](https://its.1c.ru/db/v8325doc/bookmark/adm/TI000000365).

## Запуск сервера

Команда `docker compose up -d` запускает сервис из переменной `COMPOSE_PROFILES` в `.env`,
в `.env.example` это `server`. Чтобы вместо него работал `full`, указывается
`COMPOSE_PROFILES=full`. Одновременно сервисы не работают, потому что занимают одни и те же
порты. Поэтому перед сменой значения сервер останавливается командой `docker compose down`,
после смены она его уже не увидит.

В контейнере работают сервер 1С и сервер администрирования `ras`, через который кластером
управляют с помощью `rac`. Если любой из них завершится, контейнер перезапустится. Для образа
`full` в этих и следующих командах вместо `server` указывается `full`.

Если при запуске Docker сообщает, что порт уже занят, серверу нужны другие порты,
подробнее в разделе [Смена портов](#смена-портов).

Данные кластера хранятся в томе `srv-data`, программные лицензии в томе `licenses`,
технологический журнал в томе `logs`.

### Подключение к серверу

Клиенты подключаются к серверу по имени из переменной `ONEC_HOSTNAME`, по умолчанию
`onec-server`. На компьютере клиента это имя должно указывать на Docker-хост, например
строкой `<IP Docker-хоста> onec-server` в файле `hosts`. Если порт менеджера кластера
изменён, он указывается после имени: `onec-server:<ONEC_REGPORT>`. Менять имя после первого
запуска не стоит, кластер зарегистрирован под ним.

Если клиент работает на той же Windows-машине, что и Docker Desktop, в `hosts` указывается
не IP машины, а IP виртуальной машины WSL. Его выводит команда
`wsl -d docker-desktop ip -4 addr show eth0`, после перезапуска Windows или WSL он может
измениться.

### Автономный сервер

Вместо кластера контейнер может запустить автономный сервер `ibsrv`. Ему не нужны лицензия
на сервер и СУБД, он обслуживает одну файловую базу и отдаёт её по HTTP. Для этого
в `compose.override.yaml` меняются команда и порты:

```yaml
services:
  server:
    command: ibsrv
    ports: !override
      - "8314:8314"
```

Контейнер становится `healthy`, когда сервер готов принимать запросы. Порт он открывает
на несколько секунд раньше, поэтому ждать лучше состояния контейнера, а не порта.

При первом запуске контейнер создаёт пустую файловую базу в томе `srv-data`. При следующих
запусках база уже есть, и он её не трогает. База открывается в тонком клиенте и в браузере
по адресу `http://localhost:8314`.

Вместо пустой базы контейнер может взять готовую. Для этого файл базы `1Cv8.1CD` или
выгрузка `.dt` подключается в контейнер, а путь к нему внутри контейнера задаётся
в переменной `ONEC_INFOBASE_SOURCE`:

```yaml
services:
  server:
    command: ibsrv
    environment:
      ONEC_INFOBASE_SOURCE: /seed/1Cv8.1CD
    volumes:
      - ./base:/seed:ro
```

Файл `.1CD` копируется в том `srv-data`, выгрузка `.dt` загружается в новую базу. Формат
определяется по содержимому файла, поэтому его имя в контейнере может быть любым. Исходный
файл не меняется, но на время копирования база в нём должна быть закрыта. Переменная
действует только при первом запуске. Когда база в томе уже есть, файл не читается,
и подключать его не обязательно.

Ключи `ibsrv` указываются после команды, например `command: ibsrv --name=demo --http-port=9000`.
С `ONEC_DEBUG=true` включается отладка по HTTP на порту из `ONEC_DEBUG_PORT`, его тоже нужно
опубликовать.

Если в ключах задано своё расположение данных или базы, например `--data`, `--db-path`
или `--config`, контейнер базу не создаёт и переменную `ONEC_INFOBASE_SOURCE` не учитывает,
базу нужно создать заранее через `ibcmd`.
Со своим файлом настроек из `--config` адрес, на котором слушает сервер, берётся из него.

Постоянные настройки автономного сервера удобнее держать в файле `ibsrv.yml` рядом
с остальными [файлами настроек платформы](#файлы-настроек-платформы). Если он там есть,
сервер запускается с ним вместо файла из образа:

```yaml
server:
  address: any
  port: 9000
infobase:
  name: demo
```

Без строки `address: any` сервер слушает только `localhost`, и опубликованный порт
не отвечает. Заготовку со всеми параметрами выводит команда `ibcmd server config init`.

Для сервиса `full` в списке портов оставьте ещё порты дисплея `127.0.0.1:5900:5900`
и `127.0.0.1:6080:6080`.

### Выполнение команд в контейнере

По умолчанию контейнер запускает сервер `ragent` вместе с `ras`. Команда `ras` запускает
только сервер администрирования, команда `ibsrv` запускает [автономный сервер](#автономный-сервер),
а любая другая команда выполняется как есть.
Дополнительные ключи сервера указываются после `ragent`, например `ragent -pingTimeout 30000`.
Само слово `ragent` можно опустить: если команда начинается с ключа, запускается сервер.
Ключи `-port`, `-regport`, `-range`, `-d` и `-seclev` контейнер задаёт сам и в команде
их не принимает. Порты меняются переменными из раздела [Смена портов](#смена-портов).
Утилиты платформы, например `rac` и `ibcmd`, вызываются по имени.

Оболочку в работающем сервере открывает команда:

```sh
docker compose exec server bash
```

Отдельный контейнер из того же образа, не связанный с работающим сервером, запускается так:

```sh
docker run --rm -it onec-devops/1cv8-server:8.3.25.1633 bash
```

Команда `docker compose run server` для этого не подходит, потому что создаёт второй
контейнер с тем же именем хоста и MAC-адресом в сети работающего сервера.

Каталог с данными сервера `/home/usr1cv8/.1cv8` объявлен в образе томом. Сервис
в `compose.yaml` хранит его в именованном томе, как и лицензии с технологическим журналом.
Если сервер запускается через `docker run`, тому с данными тоже нужно дать имя, например
`-v onec-data:/home/usr1cv8/.1cv8`. Иначе Docker создаст безымянный том, и следующий контейнер
его не подхватит. Каталоги `/var/1C/licenses` и `/var/log/1C` томами не объявлены, без `-v`
их содержимое пропадает вместе с контейнером.

### Запуск от другого пользователя

Контейнер работает от пользователя `usr1cv8` с UID и GID 999. Если команда пишет в каталог
хоста, например сохраняет туда файл конфигурации, контейнер можно запустить от своего
пользователя ключом `--user`. Тогда файлы на хосте будут принадлежать ему:

```sh
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/work" onec-devops/1cv8-server:8.3.25.1633 \
    ibcmd infobase create --db-path=/work/ib
```

Сервер с томами запускается без `--user`. Данные в томах принадлежат пользователю 999,
и другой пользователь не сможет их изменить.

## Запуск клиентов

Клиенты запускаются в работающем контейнере `full`, например после
`docker compose exec full bash`. Экрана у контейнера нет, поэтому вместе с сервером
в нём запускается виртуальный дисплей Xvfb, и клиенты открываются на нём. Разрешение
дисплея задаётся переменными `SCREEN_WIDTH` и `SCREEN_HEIGHT`.

Дисплей виден в браузере по адресу `http://localhost:6080`, его показывает веб-клиент
[noVNC](https://novnc.com). Порт на хосте задаётся переменной `NOVNC_PORT`. Обычный
VNC-клиент подключается к порту из `VNC_PORT`, по умолчанию 5900.

Пароль задаётся переменной `VNC_PASSWORD`, тогда его спрашивают и VNC-клиент, и noVNC.
Его можно передать и файлом, например секретом Docker. Путь к файлу в контейнере
указывается в переменной `VNC_PASSWORD_FILE`, она важнее `VNC_PASSWORD`. Пример
для `compose.override.yaml`:

```yaml
services:
  full:
    environment:
      VNC_PASSWORD_FILE: /run/secrets/vnc_password
    secrets:
      - vnc_password

secrets:
  vnc_password:
    file: ./vnc_password.txt
```

На хосте порты дисплея открыты только для самой машины. Другим контейнерам в той же сети
Docker дисплей доступен напрямую, поэтому в общей сети задайте пароль.

Дисплей общий для всех клиентов в контейнере. Если клиенту нужен отдельный чистый дисплей,
например в автоматическом прогоне, команда запускается через `xvfb-run -a`. Такой дисплей
существует, пока работает команда, и в браузере не виден.

Если общий дисплей не нужен, он отключается строкой `START_DISPLAY=false` в `.env`. Тогда
в контейнере не запускаются Xvfb, Fluxbox, VNC-сервер и noVNC, а клиентам остаётся
`xvfb-run -a`.

Тонкий клиент по умолчанию не открывает файловые базы напрямую. Файловая база создаётся
через `ibcmd` и публикуется через `ibsrv`, а клиент подключается к ней по HTTP с ключом `/WS`.
Контейнер делает это сам, если запущен как [автономный сервер](#автономный-сервер), тогда
клиент запускается командой `1cv8c ENTERPRISE /WS http://localhost:8314`.

## Смена версии платформы

1. Положите в `distr/` дистрибутив новой версии вместо прежнего.
2. Укажите новую версию в `ONEC_VERSION` в файле `.env`.
3. Пересоберите образ и перезапустите сервер:

   ```sh
   docker compose build server
   docker compose up -d
   ```

Тома при этом не удаляются: данные кластера, лицензии и технологический журнал остаются
на месте. Образ прежней версии тоже остаётся, пока его не удалить.

## Лицензии платформы

Без лицензии можно создавать базы, загружать и выгружать конфигурацию через `ibcmd`,
а также работать в тонком клиенте с базой, опубликованной через `ibsrv`, если одновременно
запущено не больше трёх клиентских сеансов. Толстому клиенту и конфигуратору лицензия нужна.

В контейнере работают только программные лицензии, аппаратные ключи защиты
не поддерживаются. Программная лицензия привязана к параметрам компьютера, в том числе
к имени хоста и MAC-адресу. Compose задаёт их явно, чтобы они не менялись при пересоздании
контейнера. Остальные параметры, например процессор и память, контейнер получает
от Docker-хоста. Файлы лицензий хранятся в томе `licenses`.

## Участие в разработке

Помочь проекту можно pull request'ом: исправлением ошибки, новой функциональностью или
улучшением документации. Крупное изменение лучше сначала обсудить в issue. Как собрать образы
и запустить тесты, рассказано в [CONTRIBUTING.md](CONTRIBUTING.md).
